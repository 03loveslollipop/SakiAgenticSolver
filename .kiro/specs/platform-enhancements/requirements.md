# Requirements Document: CTF Automation Platform Enhancements

## Introduction

This document specifies the requirements for enhancing the existing CTF Challenge Automation Platform with new features: support for additional AI agents (Gemini CLI and Mistral Vibe CLI), manual VM mode without AI agents, and automated cronjobs for writeup uploads and VM cleanup. These enhancements expand the platform's capabilities and improve operational efficiency.

## Glossary

- **Platform**: The CTF Challenge Automation Platform system
- **Dashboard**: The web-based user interface for managing VMs and sessions
- **VM**: Virtual Machine running on Azure infrastructure
- **Session**: An active VM instance working on CTF challenges
- **Agent**: An AI agent that attempts to solve CTF challenges
- **Manual_Mode**: A VM configuration without an AI agent, allowing direct SSH access for manual work
- **Gemini_CLI**: Google's Gemini AI command-line interface agent
- **Mistral_Vibe_CLI**: Mistral AI's Vibe command-line interface agent
- **Codex**: Existing OpenAI Codex agent
- **Copilot**: Existing GitHub Copilot agent
- **Cronjob**: A scheduled task that runs automatically at specified intervals
- **Northflank**: The deployment platform for running cronjobs
- **Static_Blog**: The Astro-based blog at blog.saki.02labs.me for displaying writeups
- **Writeup**: A final report generated by the Agent summarizing the challenge solution
- **VM_Cleanup**: The process of deleting VMs that have been running for too long
- **Backend**: The Python server component that manages Azure resources and API endpoints
- **Frontend**: The React-based web interface
- **User**: A registered account with credentials for accessing the Platform

## Requirements

### Requirement 1: Additional AI Agent Support

**User Story:** As a CTF player, I want to use Gemini CLI and Mistral Vibe CLI as additional AI agent options, so that I can leverage different AI models and capabilities for solving challenges.

#### Acceptance Criteria

1. WHEN a user creates a new VM, THE Platform SHALL accept "gemini-cli" as a valid agent type option
2. WHEN a user creates a new VM, THE Platform SHALL accept "mistral-vibe-cli" as a valid agent type option
3. WHEN a user selects "gemini-cli" as the agent type, THE Platform SHALL accept any available Gemini model as a valid model option
4. WHEN a user selects "mistral-vibe-cli" as the agent type, THE Platform SHALL accept any available Mistral Vibe model as a valid model option
5. WHEN a VM is created with "gemini-cli" agent type, THE Platform SHALL install and configure Gemini CLI on the VM
6. WHEN a VM is created with "mistral-vibe-cli" agent type, THE Platform SHALL install and configure Mistral Vibe CLI on the VM
7. WHEN a Gemini CLI agent starts, THE Agent SHALL have access to all configured MCP servers (writeup retrieval, documentation, web search)
8. WHEN a Mistral Vibe CLI agent starts, THE Agent SHALL have access to all configured MCP servers (writeup retrieval, documentation, web search)
9. THE Gemini CLI agent SHALL maintain changelog.md, discoveries.md, and generate writeup.md files following the same documentation standards as existing agents
10. THE Mistral Vibe CLI agent SHALL maintain changelog.md, discoveries.md, and generate writeup.md files following the same documentation standards as existing agents

### Requirement 2: Manual VM Mode

**User Story:** As a CTF player, I want to create VMs without AI agents for manual work, so that I can solve challenges myself or use custom tools not supported by the AI agents.

#### Acceptance Criteria

1. WHEN a user creates a new VM, THE Platform SHALL accept "manual" as a valid agent type option
2. WHEN a user selects "manual" as the agent type, THE Platform SHALL not require a model selection
3. WHEN a VM is created with "manual" agent type, THE Platform SHALL NOT install any AI agent on the VM
4. WHEN a VM is created with "manual" agent type, THE Platform SHALL still execute the Setup_Script to install all required tools (z3, cryptographic utilities, decompilers, debuggers)
5. WHEN a VM is created with "manual" agent type, THE Platform SHALL still download all Challenge_Files from the provided URLs
6. WHEN a VM is created with "manual" agent type, THE Platform SHALL still create instructions.md file containing the user-provided challenge instructions
7. WHEN a VM is created with "manual" agent type, THE Platform SHALL NOT create BASE_PROMPT.md, AGENT.md, or start any AI agent
8. WHEN a VM is created with "manual" agent type, THE Platform SHALL still create TOOLS.md file documenting all installed tools and their versions
9. WHEN a VM is created with "manual" agent type, THE Platform SHALL still configure MCP servers for potential future use
10. WHEN a user accesses a "manual" mode VM through the terminal interface, THE Platform SHALL provide a standard shell prompt without AI agent interaction
11. WHEN displaying a "manual" mode session in the Dashboard, THE Frontend SHALL show "Manual" as the agent type
12. WHEN displaying a "manual" mode session in the Dashboard, THE Frontend SHALL not display agent model information

### Requirement 3: Writeup Upload Cronjob

**User Story:** As a system administrator, I want newly generated writeups to be automatically uploaded to a static blog, so that all solutions are publicly accessible and organized.

#### Acceptance Criteria

1. THE Platform SHALL deploy a cronjob on Northflank that runs every 15 minutes
2. WHEN the cronjob runs, THE Platform SHALL query MongoDB for writeups that have not been uploaded to the static blog
3. WHEN the cronjob finds new writeups, THE Platform SHALL format each writeup for the static blog
4. WHEN formatting a writeup, THE Platform SHALL extract metadata (category, technologies, completion timestamp, agent type, agent model)
5. WHEN formatting a writeup, THE Platform SHALL convert the writeup content to a blog post format with proper frontmatter
6. WHEN a writeup is formatted, THE Platform SHALL commit it to the GitHub repository for the static blog (blog.saki.02labs.me)
7. WHEN a writeup is committed to GitHub, THE Platform SHALL push the changes to trigger a rebuild of the static blog
8. WHEN a writeup is successfully uploaded, THE Platform SHALL mark it as "uploaded" in MongoDB to prevent duplicate processing
9. WHEN the cronjob encounters an error during upload, THE Platform SHALL log the error and continue processing other writeups
10. WHEN the cronjob completes a run, THE Platform SHALL log the number of writeups processed and any errors encountered
11. THE cronjob SHALL handle rate limiting and authentication for GitHub API operations
12. THE cronjob SHALL be deployed as a containerized application on Northflank with appropriate environment variables (MongoDB connection string, GitHub token, etc.)

### Requirement 4: VM Cleanup Cronjob

**User Story:** As a system administrator, I want to automatically delete VMs that have been running for too long, so that I don't incur unnecessary Azure costs and keep the system clean.

#### Acceptance Criteria

1. THE Platform SHALL deploy a cronjob on Northflank that runs every hour
2. WHEN the cronjob runs, THE Platform SHALL query MongoDB for sessions with status "running" that were created more than 48 hours ago
3. WHEN the cronjob finds expired sessions, THE Platform SHALL delete the associated Azure VMs
4. WHEN deleting an Azure VM, THE Platform SHALL also delete associated resources (network interfaces, public IPs, disks)
5. WHEN a VM is successfully deleted, THE Platform SHALL update the session status to "deleted" in MongoDB
6. WHEN a VM deletion fails, THE Platform SHALL log the error and update the session status to "cleanup_failed" in MongoDB
7. WHEN the cronjob encounters an error during VM deletion, THE Platform SHALL log the error and continue processing other sessions
8. WHEN the cronjob completes a run, THE Platform SHALL log the number of VMs deleted and any errors encountered
9. THE cronjob SHALL handle Azure authentication and API rate limiting
10. THE cronjob SHALL be deployed as a containerized application on Northflank with appropriate environment variables (Azure credentials, MongoDB connection string, etc.)
11. THE cronjob SHALL send a notification (email or webhook) when it fails to delete a VM after multiple attempts
12. THE Platform SHALL provide an API endpoint to manually trigger VM cleanup for testing purposes

### Requirement 5: Backend API Updates

**User Story:** As a developer, I want the backend API to support the new features, so that the frontend can properly interact with enhanced VM configurations.

#### Acceptance Criteria

1. WHEN the backend receives a VM creation request with "gemini-cli" agent type, THE Backend SHALL validate the request and proceed with VM creation
2. WHEN the backend receives a VM creation request with "mistral-vibe-cli" agent type, THE Backend SHALL validate the request and proceed with VM creation
3. WHEN the backend receives a VM creation request with "manual" agent type, THE Backend SHALL validate the request and proceed with VM creation
4. WHEN the backend creates a session with "manual" agent type, THE Backend SHALL store the session in MongoDB with agent_type="manual" and agent_model=null
5. WHEN the backend retrieves session details for a "manual" mode session, THE Backend SHALL return agent_type="manual" and agent_model=null
6. THE Backend SHALL update the VMCreationRequest model to include "gemini-cli", "mistral-vibe-cli", and "manual" as valid agent_type values
7. THE Backend SHALL update the Session model to support "gemini-cli", "mistral-vibe-cli", and "manual" as valid agent_type values
8. THE Backend SHALL update the VM setup service to handle installation of Gemini CLI and Mistral Vibe CLI
9. THE Backend SHALL update the VM setup service to skip AI agent installation for "manual" mode
10. THE Backend SHALL provide an API endpoint to trigger manual VM cleanup (for testing cronjob functionality)

### Requirement 6: Frontend Updates

**User Story:** As a user, I want the frontend to support the new agent options and manual mode, so that I can easily create and manage all types of VMs.

#### Acceptance Criteria

1. WHEN a user accesses the VM creation form, THE Frontend SHALL include "Gemini CLI" and "Mistral Vibe CLI" as options in the agent type dropdown
2. WHEN a user accesses the VM creation form, THE Frontend SHALL include "Manual (No Agent)" as an option in the agent type dropdown
3. WHEN a user selects "Gemini CLI" as the agent type, THE Frontend SHALL display a dropdown for selecting Gemini models
4. WHEN a user selects "Mistral Vibe CLI" as the agent type, THE Frontend SHALL display a dropdown for selecting Mistral Vibe models
5. WHEN a user selects "Manual (No Agent)" as the agent type, THE Frontend SHALL hide the model selection dropdown
6. WHEN displaying a session with "manual" agent type in the Dashboard, THE Frontend SHALL show "Manual" instead of an agent type/model
7. WHEN viewing a "manual" mode session detail, THE Frontend SHALL not display AGENT.md or BASE_PROMPT.md tabs (since they don't exist)
8. WHEN viewing a "manual" mode session detail, THE Frontend SHALL still display TOOLS.md, changelog.md, and discoveries.md tabs if files exist
9. THE Frontend SHALL update the Session interface to support "gemini-cli", "mistral-vibe-cli", and "manual" as valid agent_type values
10. THE Frontend SHALL update the VMCreationRequest interface to support the new agent types

### Requirement 7: Error Handling and Validation

**User Story:** As a system, I want proper error handling and validation for the new features, so that users get clear feedback and the system remains stable.

#### Acceptance Criteria

1. WHEN a user attempts to create a VM with an invalid combination of agent type and model, THE Platform SHALL return a descriptive validation error
2. WHEN the VM setup fails to install Gemini CLI, THE Platform SHALL capture the error and make it available to the user
3. WHEN the VM setup fails to install Mistral Vibe CLI, THE Platform SHALL capture the error and make it available to the user
4. WHEN the writeup upload cronjob fails to connect to MongoDB, THE Platform SHALL log the error and retry with exponential backoff
5. WHEN the writeup upload cronjob fails to push to GitHub, THE Platform SHALL log the error and retry with exponential backoff
6. WHEN the VM cleanup cronjob fails to authenticate with Azure, THE Platform SHALL log the error and send a notification
7. WHEN the VM cleanup cronjob encounters a VM that cannot be deleted (e.g., in use), THE Platform SHALL log the warning and skip that VM
8. THE Platform SHALL log all cronjob executions with timestamps and outcomes
9. THE Platform SHALL provide health check endpoints for both cronjobs
10. THE Platform SHALL implement circuit breakers for external API calls (GitHub, Azure) in the cronjobs
